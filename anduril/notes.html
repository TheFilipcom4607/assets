How it works

This page runs Anduril itself. Not a re-implementation, not a description of the UI: the same C source that gets flashed onto a flashlight, compiled to WebAssembly and given simulated hardware to talk to.

What is real

Every build here is produced by compiling ToyKeeper's Anduril at a released tag, unmodified. Anduril builds as one big translation unit, so the whole firmware — the FSM microkernel, the event decoder, the ramp tables, the config menus, thermal regulation, low-voltage protection, the aux LED logic, the blinkies — is compiled exactly as it is upstream. When you press the button, the click is decoded by fsm/wdt.c and dispatched by fsm/events.c to whichever state function is on top of Anduril's own state stack. The instrument panel is reading the firmware's own variables.

The Source panel fetches the file for the running state straight from GitHub at the commit the build was compiled from, so you can read the code that is executing.

What is simulated

  • The MCU. An attiny1616-class part at 10 MHz. It has a periodic interrupt every 16 ms (the 62.5 Hz clock tick Anduril counts everything in), a slower 128 ms tick in standby, sleep modes, and an ADC that finishes a conversion about every 83 µs.
  • The clock. Simulated time only advances when the firmware waits: delay loops, sleeps, EEPROM writes and pin reads all cost the same number of cycles they would on the real part. The host doles out cycles in step with the wall clock, so a second in here is a second out there.
  • The pins. Older Anduril versions drive the aux LEDs by poking port registers directly, so the simulator emulates the pins: set/clear registers, direction, and the internal pull-up that Anduril uses to get a dim "low" out of an LED with no PWM on it.
  • The temperature sensor. The die heats up as a first-order lag toward whatever temperature the current output would settle at, and the sensor reports that temperature plus whatever error you dial in. The firmware only ever sees the sensor, so a sensor that reads 2 °C high makes the light throttle 2 °C early — and you can correct it from Anduril's own thermal calibration menu, exactly as on a real light.
  • The cell. Open-circuit voltage, internal resistance, sag under load and the drop before the MCU. Optionally it runs down as you use it, which is enough to trigger the firmware's low-voltage warnings.
  • The EEPROM. Backed by your browser's local storage, per version and per hardware layout, so your settings survive a reload the way they survive a battery change.

What differs from a real light

  • int is 32 bits here, 16 bits on AVR. This is the one difference that could in principle change behaviour: arithmetic that would overflow a 16-bit int on the real chip will not overflow here. Anduril avoids relying on that, but it is not something the simulator can rule out.
  • Computation is free. Only waiting costs simulated time, so the firmware's own instruction cycles are not counted. Anything timed by the clock tick or by a delay is exact; anything that depended on how long a calculation took would not be.
  • The light is generic. It is an FET+1 driver on an attiny1616 with the ramp tables Anduril ships for the Wurkkos TS10. The emitter output, currents and thermal behaviour are a model with sliders, not a specific product.
  • No PWM flicker. The panel reports duty cycle; the display shows steady brightness.
  • Aux LED brightness is approximated as off / dim / full.
  • This matrix covers aux LEDs, button LEDs and the temperature sensor. Tint ramping, multi-channel lights and dual-switch (clicky + e-switch) lights are not built here.

How the builds are made

Vercel serves static files, so nothing can be compiled on demand. Instead the sources are checked out at each release tag and compiled ahead of time with clang --target=wasm32, once per hardware combination, then run through Binaryen's --asyncify pass. Asyncify is what lets the firmware's blocking while(1) main loop and its busy-wait delays hand control back to the browser between animation frames instead of freezing the tab. Every artifact is booted and clicked once during the build; one that does not run never reaches the site.

The simulated hardware lives in sim/: an arch/sim.c that implements the same interface as Anduril's arch/attiny1616.c, a hardware definition under sim/hw/sim/ describing this imaginary light, and small stand-ins for the avr-libc headers.
